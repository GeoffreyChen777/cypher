# Cypher 0.3.47 — Permission control, a lighter question card, and less CPU

## Permissions

- **Pi chats now run under permission control** (with Pi Runtime 1.1.0.2).
  The sandbox setting each chat stored was never enforced; now it is. The
  workspace is readable and writable; the rest of the machine is readable,
  and writing there needs your approval; sensitive files (keys, `.env`
  files, credentials) need approval to read or write. Git config and hooks
  and shell startup files need approval to change. The agent's shell
  commands run in a sandbox (Seatbelt on macOS, Landlock on Linux), offline
  when they could read a secret unless you approved the network too. On a
  machine that can't sandbox, permission control stands down and says so
  once per chat.
- **Approvals once, for the chat, or always.** A request can be approved
  once, for the rest of the chat, or always (saved as a rule). Each kind of
  request can be set to deny, ask, or let a reviewing model decide first; the
  model only ever approves or hands the question to you, and sensitive
  requests always come to you.
- **Pick a chat's level with /permissions.** Ask before edits, Edit
  workspace (the default) or Full access. At Full access the composer shows
  an amber shield, which opens the same choices.
- **Settings → Permissions** edits each device's rules: approval modes, the
  reviewing model, MCP and extension tools, the network, and the extra
  sensitive, protected, writable and allowed-domain lists. It also shows
  whether the device can sandbox.

## Chats

- **A lighter question card.** The card that replaces the composer while the
  agent asks something now looks like the composer: frosted, with the
  context as plain text and soft option rows. A permission request gets its
  own layout, with the facts as rows, paths and commands in code, and the
  options weighted by what they grant. Keyboard: Y approves the narrowest
  option, C for this chat, A always, N denies, S denies and stops; ⌘↵
  approves the narrowest and plain ↵ approves nothing. Keys pressed in the
  first half second, or held down, are ignored, so a stray keystroke can't
  answer it.

## Performance

- **No more spinning before token refreshes.** A signed-in app pinned a CPU
  core for 30 seconds out of every 5 minutes while waiting to refresh its
  sign-in. It now sleeps until the refresh is due.
- **Less redrawing while sessions work.** The sidebar no longer rebuilds
  every frame while a session is working, and a running tool's spinner
  redraws at 30 fps instead of the display's full rate. With a session
  running a tool, the app's CPU dropped from about 66% to 20% in testing.

Cut at build 1 on both desktop platforms. Pi Runtime moves to 1.1.0.2,
published after the desktop release (older apps run it without permission
control); iOS stays at 0.2.0 (28).
